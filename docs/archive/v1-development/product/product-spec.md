# Knowledge Assistant — V1 Product Specification

- 状态：Final（V1 产品范围基线）
- 版本：1.0
- 日期：2026-11-06
- 仓库：[`linj6/knowledge-assistant`](https://github.com/linj6/knowledge-assistant)（private）
- 首个业务场景：技术学习知识问答
- 研发方式：Spec Coding + Codex CLI + 人工评审与验收

## 1. 产品定位

Knowledge Assistant 是面向个人知识资料的通用 AI 知识库底座。V1 以 Java 后端技术学习资料为首个真实业务场景，提供文档导入、证据检索、知识问答、来源引用与效果评估能力。底层不得硬编码 Java 技术领域规则，需使用一组非技术文档验证通用性。

V1 面向单用户、本地运行；不建设多租户 SaaS 平台。后续可演进至上下文工程、长期记忆与 Agent，但这些能力不属于 V1。

## 2. 目标与成功标准

1. **完整性**：Markdown/TXT 文件经解析、切分、双索引构建后可用于问答。
2. **可追溯**：回答引用可定位到实际检索片段与原始文档位置；不得伪造引用。
3. **可比较**：支持向量、BM25、混合 RRF、混合 RRF + Rerank 四种策略，使用固定数据与评估口径对照。
4. **可靠性**：导入失败、检索失败、重排失败、证据不足均有可识别的结果；不得静默宣称成功。
5. **通用性**：同一系统能处理 Java 技术文档与至少一组非技术文档。
6. **可复现**：提供运行说明、测试、评估数据与结果报告。

质量指标以实验建立基线，不预设混合检索或重排一定优于单路检索，不设未经验证的 QPS/SLA。

## 3. 已确认的产品决策

- D-01：V1 采用**手动文件导入**；Git 仓库自动同步延期。手动导入应支持通过 API 提交本地文件，具体传输方案在架构阶段确定。
- D-02：V1 必须实现**真正的 BM25** 词法相关性检索与向量检索，不以普通全文检索分数冒充 BM25。具体引擎在架构阶段选型。
- D-03：保留完整 P0：导入、双路检索、RRF、Rerank、问答、引用、策略对比、自动化评估。
- D-04：V1 先以 REST API 和测试完成验收；Web UI 不属于 P0。
- D-05：单体应用、清晰逻辑边界是优先方向；部署架构由 Architecture Spec 确定。

## 4. 用户与核心使用场景

**目标用户**：管理个人技术文档并希望基于证据提问的学习者。通用底座可用于其他文本知识领域。

- UC-01：创建知识库并导入 Markdown/TXT 文档，查询处理结果。
- UC-02：询问“RabbitMQ ACK 后数据库事务失败会怎样”，获得基于知识库的回答及引用。
- UC-03：询问知识库没有覆盖的事实，系统明确说明证据不足，不编造知识库事实。
- UC-04：对同一问题比较向量、BM25、RRF、RRF+Rerank 的检索结果与延迟。
- UC-05：批量执行固定评估集，生成可复现的质量对比报告。
- UC-06：导入一组非技术文档，验证领域无关性。

## 5. 功能需求与优先级

| ID | 优先级 | 需求 | 验收行为 |
|---|---|---|---|
| FR-01 | P0 | 知识库创建与查询 | 可以创建、列出、获取知识库；检索严格限定目标知识库 |
| FR-02 | P0 | 手动导入 Markdown/TXT | 返回导入任务标识与状态；不支持格式明确报错 |
| FR-03 | P0 | 文档解析与 Chunk 切分 | 保留文档 ID、Chunk ID、来源与可定位的原文位置 |
| FR-04 | P0 | 双索引构建 | 同一可检索文档的 BM25 与向量索引完成后才标记 READY |
| FR-05 | P0 | 向量检索 | 返回排序后的证据片段、分数或排序信息及来源 |
| FR-06 | P0 | 真正 BM25 检索 | 返回词法相关性排序，BM25 计算或引擎行为可验证 |
| FR-07 | P0 | 混合检索与 RRF | 两路候选按排名融合，保留可追踪的候选与排名信息 |
| FR-08 | P0 | Rerank | 可对融合候选重排，记录配置、结果与额外耗时 |
| FR-09 | P0 | RAG 问答 | 基于限定知识库中的检索证据生成答案，记录生成状态 |
| FR-10 | P0 | 来源引用 | 引用指向实际参与生成的证据，能够定位原始文档 |
| FR-11 | P0 | 策略对照 | 同一查询可分别运行四种策略并对照结果、配置和耗时 |
| FR-12 | P0 | 自动化评估 | 固定数据集运行、保存指标与逐例结果，支持复跑 |
| FR-13 | P1 | 文档删除 | 删除文档与关联索引，避免残留可检索片段 |
| FR-14 | P1 | 文档更新 | 修改后重建索引，避免旧新版本混用 |
| FR-15 | P1 | 流式生成 | SSE 返回逐步生成内容，最终结果仍包含引用与状态 |
| FR-16 | P2 | PDF 等更多格式 | 后续扩展文档解析器 |
| FR-17 | P2 | Web UI | 后续可视化知识库与问答 |
| FR-18 | P2 | Git 仓库自动同步 | 后续复用统一导入处理链路 |

**范围说明**：P1/P2 不属于 V1 发布阻断项。P0 的“创建与查询”不隐含删除或修改知识库。V1 文档发生变化时允许通过明确的新导入处理；自动版本替换属于 P1。

## 6. 关键业务规则

### 6.1 导入与索引生命周期

- 导入任务至少具有 `RECEIVED`、`PROCESSING`、`READY`、`FAILED` 可识别状态；是否细分解析/Embedding/索引阶段由架构决定。
- READY 必须表示本次导入要求的两类索引均可检索。部分成功不得冒充 READY。
- 相同知识库内重复导入相同内容应被识别，不能无提示地产生重复可检索内容；使用内容哈希还是其他机制由架构确定。
- 外部模型或索引服务失败时，保留诊断信息，并支持可重复执行的恢复操作；恢复方式由架构确定。
- 失败/处理中数据不进入正式问答检索。需要验证孤儿索引和部分成功的处理方式。

### 6.2 检索

- S1：向量检索；S2：BM25；S3：向量 + BM25 + RRF；S4：S3 + Rerank。
- RRF 按候选排名融合，不能直接把异构分数当成同一尺度相加。
- 检索必须限定知识库边界；没有足够候选时允许返回少于 K 条。
- 应能记录候选集合、最终排名、关键参数、检索及重排耗时，以支持实验复现。
- 不假设 S4 一定优于 S1/S2/S3；实验结果不达预期也可验收，但必须说明原因与局限。

### 6.3 问答与引用

- 模型输入包含用户问题与已选证据；文档内容视为不可信数据，不可覆盖系统规则。
- 证据不足、检索为空时明确说明无法从知识库确认；不得编造文档来源。
- 引用必须对应真实证据片段；不允许引用未参与答案生成的文档来装饰答案。
- 返回结构应能区分成功回答、证据不足、外部依赖失败等状态。
- V1 为单轮独立问答，不承诺跨轮记忆或指代消解。

## 7. 评估需求

### 7.1 数据集

建议初始建立 20–30 条带人工标注的测试问题，覆盖：精确术语、语义改写、跨片段/跨文档证据、易混淆概念、无答案问题；另有小型非技术文档集。

每例至少包含问题、知识库/数据版本、可答性标记、相关证据标识或判断依据；有答案的样本记录预期事实要点。评估数据不得泄漏到在线问答的 Prompt 中。

### 7.2 指标与对照

- 检索：Hit@K、Recall@K、MRR；说明多相关证据的标注口径。
- 生成：事实结论正确性、引用是否支持结论、拒答是否合适、整例是否通过。
- 性能：各检索通道、融合、Rerank、生成阶段耗时；可记录 Token 用量与外部调用成本。
- 四种策略须使用同一数据快照与相同查询集，记录模型、索引和参数版本。
- 不适用指标单独标记 N/A，不计为成功或失败；报告包含分子、分母与逐例结果。

## 8. 非功能需求

- **安全**：密钥仅从环境或安全配置读取，不提交仓库；限制文件大小/类型；防范路径穿越及文档内提示注入。
- **隔离**：所有检索、引用与评估限定指定知识库；跨知识库泄漏为阻断缺陷。
- **一致性**：导入状态与可检索索引状态一致，异常后可核查。
- **可测试**：纯逻辑离线单元测试，外部依赖集成测试；测试不得依赖不可控的在线模型结果才能全部通过。
- **可观测**：记录 request/import ID、阶段状态、耗时、失败类别；避免记录密钥和敏感原文。
- **可维护**：通用知识库逻辑不得硬编码 Java 术语；模块职责清晰。
- **部署**：V1 可由开发者按 README 在本地启动；不要求生产级高可用与集群。
- **性能**：先记录实验基线，暂不设未经测量的吞吐与时延 SLA。

## 9. V1 非目标

多租户 SaaS、RBAC、Git 自动同步、PDF/多模态、长期记忆、Agent、自主规划、复杂工作流、生产级高并发、微服务拆分、完整 Web UI 均不属于 V1 P0。

## 10. 里程碑与发布门槛

| 里程碑 | 目标 | 必要证据 |
|---|---|---|
| M0 | Spec 与工程准备 | Product Spec、Architecture Spec、任务计划 |
| M1 | 导入与双索引 | 导入成功/失败/重复场景测试 |
| M2 | 四种检索策略 | 固定候选、RRF、Rerank 对照测试 |
| M3 | 问答与引用 | 有答案、无答案、错误引用防护测试 |
| M4 | 评估闭环 | 逐例报告、指标分母、策略对比与耗时 |
| M5 | 工程验收 | 自动化测试、README、故障场景、非技术领域验证 |

发布需满足所有 P0 的功能验收、跨知识库隔离、失败状态可识别、评估可复现、无伪造引用、运行文档可独立执行。指标结果可以不优于基线，但不得省略或虚构。

## 11. 后续演进与边界

- V2：上下文工程与 Memory。区分外部知识文档与用户交互记忆；复用检索能力，但使用不同生命周期和数据语义。
- V3：Agent 与 Tools。将知识检索等能力作为受控工具复用，不重复实现检索逻辑。
- V4：可观测性与质量治理深化，复用 V1 的评估基础。

这些是路线方向，不作为 V1 的隐性开发要求。不得为尚未明确的未来需求提前建设通用插件平台或复杂抽象。

## 12. 架构阶段待定事项（不影响 Product Spec 定稿）

1. BM25 引擎及中英文分词策略、与向量索引的部署关系。
2. 文档元数据、Chunk、导入任务与索引版本的数据模型。
3. 文件导入 API、文件存储方式与大小上限。
4. 模型、Embedding、Rerank 供应商及接口抽象。
5. 文档处理同步/异步方式、失败恢复与索引发布机制。
6. 引用定位格式、上下文预算及问答输出协议。
7. 评估集组织、运行入口、测试分层和报告格式。

## 13. 开发协作规则

- 先完成 Spec 和架构评审，再拆分小任务交给 Codex CLI。
- 每个任务包含目标、范围、非目标、验收标准和测试证据。
- **所有代码以通俗易懂、易于维护为优先原则；主流程与重要逻辑必须有准确的中文注释**，避免仅用抽象设计模式堆砌复杂度。
- 小步提交，保持文档与实现同步；不得修改无关实验或伪造结果。
- 每个里程碑人工评审，重点验证业务边界、失败行为和 AI 质量。
